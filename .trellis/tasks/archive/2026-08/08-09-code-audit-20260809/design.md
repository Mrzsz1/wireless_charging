# 技术审查设计

## 1. 审查边界

审查采用“证据先行、跨层追踪、测试复核”的只读流程。入口从现有 Graphify 图和 CodeGraph 符号开始，随后只精读与风险路径相关的源文件、配置和测试。审查结果写入当前任务目录，不改业务代码。

## 2. 证据来源与优先级

1. 当前工作区、Git diff/status、项目 PRD 与 Trellis 规范。
2. CodeGraph 的符号源代码与调用路径。
3. `graphify query/path/explain` 的模块关系和已有测试节点。
4. 源文件、配置、测试和构建脚本的逐行复核。
5. 可重复的 lint、type-check、测试、构建和最小复现命令。

结论必须优先引用 2–5 项的直接证据；Graphify 只用于导航，不作为唯一真相。

## 3. 检查维度

### 3.1 正确性与状态

- Tauri command 的输入/输出、错误类型和前端调用是否一致。
- repository root、workspace、session、active task 和知识库索引是否在不同路径/重启/重命名后保持一致。
- 增量索引的新增、修改、重命名、删除和失败回滚是否完整。

### 3.2 安全与数据完整性

- 路径穿越、任意文件覆盖、zip 解压、命令参数拼接和密钥持久化。
- 下载/上传请求是否泄漏凭据，缓存是否跨库污染。
- 数据库事务、原子写入、临时文件和失败重试是否可能造成半成品。

### 3.3 前端交互与跨层契约

- 页面加载、空目录、错误、取消和重复点击状态。
- Tauri invoke 命令名与 payload 字段、序列化类型、日期/路径格式。
- 窗口控制、侧栏展开、持久化恢复和异步请求竞态。

### 3.4 可验证性

- 测试是否覆盖实际生产路径，而非只验证测试夹具自身。
- 每个关键 bug 类别是否有回归测试或明确的测试缺口。
- 构建产物和运行时配置是否与源码约定一致。

## 4. 结论模型

报告中的每项发现使用固定字段：`ID`、`级别`、`置信度`、`位置`、`证据`、`复现`、`影响`、`根因`、`现有覆盖`、`建议`。严重级别只依据实际影响，置信度分为 High/Medium/Low；Low 只进入待验证风险，不进入已确认 bug 数量。

## 5. 兼容性与回滚

- 审查不改变业务源代码，因此无运行时迁移和回滚风险。
- 任务文档和报告均可独立删除；若审查过程中生成临时文件，完成后清理。
- 若测试需要生成数据库、缓存或构建目录，使用临时目录或项目既有忽略目录，避免污染 Git。
