# 客户端文献添加与自动入库

## Goal

在 Windows 研究工作台中提供一站式“文献入库”，使用户无需调用脚本即可完成本地 PDF 手动添加、自动发现候选的人工确认添加，以及经过显式授权和严格规则约束的自动添加，同时保持 Raw → Canonical → Wiki → Graphify 的治理边界、来源可追溯性、失败可恢复性与正式知识库质量。

## Background

- 当前编译中心已经提供 `discover`、`parse`、`compile_a`、`lint`、`graphify_update` 与 `full_pipeline` 受控任务，并记录状态、日志、生成物、重试、取消和回滚；现有界面以底层任务参数为中心，缺少面向“添加文献”的完整产品流程。
- `tools/paper_search.py` 已能从 arXiv、OpenAlex、Tavily、SerpApi 发现、评分和去重候选，结果只写入 `raw/inbox/auto-discovered/runs/`。
- `tools/paper_triage.py` 已定义 `pending | selected | rejected | promoted` 状态，可保存人工备注并下载已选开放 PDF，但客户端尚无候选管理界面。
- `tools/mineru_to_md.py` 已支持单个/批量 PDF、200MB 上限、一文一夹 canonical、来源 frontmatter、失败状态和 dry run。
- 根 `prd.md` 当前规定自动发现只能写 inbox、不得自动晋升；用户已批准将该约束扩展为“两级自动化”：默认只准备候选，显式开启后才允许满足严格规则的候选无人值守进入正式流水线。

## Requirements

### R1. 独立入口

- 客户端新增一级导航“文献入库”。
- 页面包含“手动添加”“待确认”“自动添加”三个标签。
- 编译中心继续负责底层任务、实时日志、失败诊断、重试、暂停、回滚和生成物；文献入库页面不得复制一套独立任务历史。

### R2. 本地 PDF 手动添加

- 支持系统文件选择器选择单个或多个 PDF。
- 采用“选择文件 → 预检查与确认 → 开始入库”，确认前不得向知识库复制、解析或编译。
- 预检查展示文件名、大小、原路径、PDF 有效性、200MB 限制、采集来源 `manual_upload`、重复检测结论和预计执行/写入范围。
- 重复检测命中的文件默认不勾选；用户可明确选择重新处理，且该决定必须进入审计记录。
- 用户确认后执行复制到受控 inbox/canonical、MinerU、A 编译、Lint、本地索引刷新和 Graphify 更新。

### R3. 待确认候选

- 展示所有自动发现候选及其标题、作者、年份、摘要、来源、命中主题、相关度分数与理由、DOI/arXiv、开放获取、PDF、本地文件、重复状态和生命周期状态。
- 支持搜索、状态/来源/全文筛选、排序、单项与批量选择。
- 支持“确认添加”“仅下载”“拒绝”“稍后处理”以及人工备注。
- “确认添加”在最终摘要确认后执行下载、晋升 canonical、MinerU、A 编译、Lint、索引和 Graphify；成功后提供正式文献页入口。
- “仅下载”只准备候选 PDF，不得使候选成为 canonical 或正式 Wiki 证据。
- 失败候选保留原始元数据、失败阶段和日志，并提供从失败阶段安全重试的入口。

### R4. 两级自动化

- 默认级别为“自动准备”：发现、去重、评分并下载符合开放获取条件的 PDF，结果只进入待确认队列。
- 用户在设置中显式开启“自动入库”后，合格候选才可无人值守进入 canonical 并完成正式流水线。
- 关闭自动入库后只影响未来运行，不中断当前已明确启动的任务，也不回退已经正式入库的文献。
- `problem`、`idea`、新主题 Map、正式词表修改、删除/合并/关键 claim 改写始终不得由自动入库执行。

### R5. 自动入库默认资格

候选必须同时满足：

- 属于已配置研究主题；
- 相关度分数 `>= 8.0`；
- 标题至少命中一个领域关键词；
- 具有 DOI 或 arXiv ID；
- 具有可实际下载的开放 PDF；
- 与现有 Wiki、canonical 和候选队列中的 DOI、arXiv ID、规范化标题及文件哈希均不重复；
- PDF 下载与基本格式检查通过；
- 每次最多正式自动入库 3 篇，其余仍留在待确认队列。

相关度阈值和单次上限可配置；首次启用使用以上保守默认值。

### R6. 自动与手动触发

- 不安装 Windows 服务、Windows 计划任务，也不使用后台定时器。
- 自动触发：知识库恢复/打开完成后，客户端启动弹窗询问是否运行配置好的流程。
- 手动触发：“自动添加”标签提供“立即运行”按钮，随时执行与启动询问相同的配置和权限。
- 启动弹窗提供：“本次运行”“今天不再提醒”“取消”。
- “今天不再提醒”只抑制当前自然日后续启动询问，不关闭手动按钮或未来日期提示。
- “取消”只关闭本次弹窗，不记录当日抑制，下次启动仍可询问。
- “本次运行”应明确展示将运行“自动准备”还是“自动入库”。

### R7. 状态、审计与恢复

- 三种入口最终复用编译中心受控执行、固定命令允许列表、仓库写互斥、事件流、日志脱敏、取消、重试和回滚机制。
- 自动正式入库按单篇隔离；某篇失败不得阻塞其他合格文献，也不得产生伪成功来源页。
- UI 显示候选/文件的阶段、进度、失败原因、最近日志、可执行恢复动作和关联编译任务。
- 启动、手动触发、自动资格判断、人工覆盖重复项、确认/拒绝/仅下载等决定均可追溯。

### R8. 重复检测

- 自动候选按 DOI、arXiv ID、规范化标题依次匹配；已有本地 PDF 时再比较 SHA-256。
- 手动 PDF 至少执行 SHA-256、文件名/规范化标题和 canonical/Wiki 来源路径检查；无法可靠提取 DOI 时不得伪造 DOI 判断。
- 重复结论需包含匹配类型和已存在对象入口，不只返回布尔值。

### R9. 降级与依赖

- 缺少 MinerU Key、Codex CLI、Graphify、网络或开放 PDF 时，界面显示缺失依赖及可执行修复说明。
- “仅下载”、自动准备、解析和正式编译分别按实际能力启用；不得因为后续能力缺失而伪装整条流水线可用。
- 自动准备可以在 Codex/Graphify 不可用时运行；正式入库必须通过全部必需能力检查。

### R10. 治理与兼容

- 自动候选在人工确认或自动资格策略通过前不得成为正式 Wiki 证据。
- Raw 正文保持只读；正式写入继续遵循 `AGENTS.md`、schema、A 编译、Lint、library-status 和日志要求。
- 同步更新根 `prd.md` 中“自动发现不得自动晋升”的旧约束，记录“显式启用 + 严格资格 + 单篇隔离”的新产品决策。
- 旧 discovery manifest 缺少新增结构化字段时必须可读取、可迁移，不要求用户清空历史候选。

## Acceptance Criteria

- [ ] AC1 / R1：侧栏存在“文献入库”，三个标签均可访问；编译中心仍能打开同一批入库任务详情。
- [ ] AC2 / R2：用户可选择多个仓库外 PDF，在无知识库写入的预检查页发现无效、超限和重复项，确认后逐篇显示完整入库结果。
- [ ] AC3 / R3：候选列表能读取历史与最新 discovery manifest，完成搜索、筛选、排序、确认、仅下载、拒绝、稍后处理和批量操作。
- [ ] AC4 / R3：确认添加成功后候选为 `promoted`、canonical 目录及正式 source 页可追溯；仅下载后仍不是正式证据。
- [ ] AC5 / R4-R5：默认运行只准备候选；显式开启自动入库后，仅满足全部默认资格的最多 3 篇候选进入正式流水线，不合格项显示具体原因。
- [ ] AC6 / R6：启动弹窗三个动作符合自然日抑制规则；手动“立即运行”始终可用并复用相同配置。
- [ ] AC7 / R7：单篇失败不阻塞同批其他文献，失败项无伪成功 source，可从失败阶段重试并在编译中心查看关联日志。
- [ ] AC8 / R8：DOI、arXiv、标题和文件哈希重复场景均有测试，UI 显示匹配原因和已有对象。
- [ ] AC9 / R9：缺少各依赖时对应操作被准确降级并显示原因；可用的较早阶段仍可独立运行。
- [ ] AC10 / R10：旧 manifest 兼容测试通过，根 PRD 与客户端 README 已同步更新。
- [ ] AC11：前端状态测试、Python 工具测试、Rust 测试、TypeScript 构建、桌面验证脚本、Wiki Lint、Wiki 评测和两本书 Recall@5 门禁全部通过。
- [ ] AC12：生成新的 Windows release/NSIS 安装包并通过启动与“文献入库”导航冒烟。

## Out of Scope

- 客户端关闭时继续运行的 Windows 服务或计划任务。
- 任意网页、Blog、PPT 直接成为正式来源。
- 自动创建 `problem`、`idea`、新 Map 或自动修改 `vocab.yaml`。
- 取消所有人工边界的“搜索到什么就全部写入 Wiki”。
- 云端账户、多用户审批或跨设备同步。

## Planning Decision

本任务保持为一个跨层集成任务，不拆分子任务。前端、Tauri DTO、候选状态、编译任务和 Python 流水线共享同一组状态契约，拆分会增加中间不兼容窗口；实施计划以明确阶段和每阶段回滚点控制风险。
